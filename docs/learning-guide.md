# 从当前第二课走到可讲清楚的实习项目

你正在学习的 `thread_id` 与 checkpointer，在本项目中对应 `agent.py` 的服务端会话配置。先用本地 demo 学业务与状态，再启用真实模型，能更容易定位问题来自哪一层。

## 第一次体验

1. 用 `customer@supportflow.local` 登录。
2. 向 AI 提问：“FastAPI 部署后返回 502，日志 Connection refused，该怎么排查？”
3. 查看知识引用和工具记录，然后继续说：“请把这个问题整理成工单。”
4. 确认前去工单中心观察：只有草稿，没有新正式工单。
5. 回来确认草稿，记录真实工单编号。
6. 退出，用工程师账号登录。找到该工单，分派给自己，改成“处理中”，补充评论。
7. 再用提问用户登录，查看进展。用另一位用户登录则不能看到这张工单。

## 逐步修改

| 阶段 | 亲手完成的实验 | 可以解释的问题 |
| --- | --- | --- |
| 状态 | 重启应用后继续原会话，再新建一段会话 | 会话历史与用户身份为什么分开？ |
| 工具 | 添加一个只读的“发布记录查询”工具，并明确数据源 | 模型如何选工具？参数和异常如何处理？ |
| 检索 | 增加你熟悉的文档及对应评测问题 | 为什么分段？为什么误召回？ |
| 事务 | 重复点击确认、并发确认、使用旧版本改状态 | 唯一约束和版本号分别解决什么问题？ |
| 真实模型 | 开启 live，观察调用次数和 Token | 固定工作流与模型自主选择工具有什么差异？ |
| 优化 | 在固定数据集上比较一种检索改动 | 改善了什么，代价是什么？ |

## 最值得继续投入的三个改动

1. **检索相关性与无答案识别**：当前只要存在词项匹配就可能返回结果。先分析离线评测中错误召回的案例，再引入重排或相关性门槛。保留独立测试集，不能只把规则调到当前 30 条样例全对。
2. **真实业务工具**：将固定模拟监控替换为你自己的演示服务健康接口，配置允许访问的服务列表与超时；不要开放任意 URL 抓取。
3. **工程演进**：引入数据库迁移、将 `App.tsx` 的各页面拆成独立模块、增补有真实浏览器的端到端测试，再考虑持久化任务调度和多实例。

## 简历与面试

可以准确描述本项目的架构与自己验证过的内容，但应区分初始 AI 辅助实现、借鉴的开源机制和后续亲自完成的改进。

面试前至少能独立解释：

- 一次请求从页面到 Agent、工具、数据库再回到页面的完整路径。
- `thread_id`、用户 ID、请求幂等键分别是什么。
- 为什么模型不能直接确认草稿。
- 同时点两次确认为什么只生成一张工单。
- 两位工程师同时修改时，版本冲突如何发生。
- BM25 的词项匹配为什么可能返回无关资料。
- 检索命中、工具成功、业务任务完成与根因验证为什么是不同指标。
- 当前单进程和 SQLite 检查点的边界，Docker / PostgreSQL 哪些内容尚未实测。
